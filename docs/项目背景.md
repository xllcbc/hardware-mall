## 一、项目起源

### 1.1 业务背景

我家在[所在城市]经营一家五金店，主营锁具和胶类两大类商品。

**锁具类商品**主要包括：门锁（防盗门锁、室内门锁、指纹锁）、挂锁、柜锁、锁芯、钥匙配件等。这类商品的特点是规格多样（不同品牌、不同型号尺寸差异大）、价格从几十元到几百元不等、客户群体包括家庭用户和工程用户。

**胶类商品**主要包括：AB胶、玻璃胶、结构胶、密封胶、美缝剂、瞬干胶等。这类商品的特点是规格多样（容量、品牌、用途不同）、易泄漏需注意包装、存储有一定时效性、客户包括家庭用户和装修师傅。

店铺经营多年，客户群体相对稳定，主要包括：附近居民（日常家用维修）、装修公司（批量采购锁具和胶类）、个体装修师傅（长期合作）、小型工程队（项目式采购）。

### 1.2 当前业务流程

目前店铺处理订单的方式比较传统，主要依赖微信沟通：

```
客户发现需求 → 添加微信好友 → 发送商品信息 → 口头描述需求 → 店家确认库存
→ 客户转账付款 → 店家安排发货 → 通过微信告知物流信息 → 客户确认收货
```

这种模式在订单量较少时尚可维持，但随着业务发展和客户数量增长，存在的问题日益突出。

## 二、痛点分析

### 2.1 沟通成本高

**问题表现**：客户需要打字或发语音描述商品，有时候商品名称不准确。比如把“玻璃胶”说成“透明胶”，把“防盗门锁”说成“大门锁”，需要反复确认才能准确理解需求。有时客户发送的图片不清晰或角度不对，无法准确判断商品型号。

**影响**：每次沟通需要多个来回，平均耗时15-30分钟，店家需要反复翻看聊天记录确认细节。

### 2.2 订单容易遗漏或混淆

**问题表现**：微信消息太多时，可能漏看客户的订单信息；不同客户的订单混在一起，难以快速统计当日有哪些订单需要处理；客户催单时需要手动翻找聊天记录。

**影响**：订单处理效率低，高峰时段每天处理20-30个订单时容易出错，曾出现过漏单情况影响客户体验。

### 2.3 库存管理不清晰

**问题表现**：不知道某个商品还剩多少库存，每次客户询价都需要去仓库实地查看；有时候客户下单后才发现没货，只能临时调货影响客户体验；无法提前预警畅销商品的补货时机。

**影响**：回复客户速度慢，部分订单因库存问题需要取消或延期。

### 2.4 无法数据化运营

**问题表现**：没有销售数据统计，不知道哪些商品卖得好、哪些是滞销品；无法分析客户的购买频次和偏好；进货决策主要凭经验，缺乏数据支撑。

**影响**：库存积压和缺货情况并存，资金周转效率低。

### 2.5 物流信息不同步

**问题表现**：客户下单时选择物流方式不够便捷（需要在微信里反复确认）；发货后物流信息需要手动发送给客户，客户无法自主查询；不同客户使用的物流偏好不同，管理困难。

**影响**：客户体验差，店家需要花费大量时间处理物流咨询。

## 三、项目定位

### 3.1 项目类型

本项目是一个**自用工具型轻量商城**，区别于商业化电商平台，有以下特点：

| 对比维度 | 商业化电商平台 | 本项目（自用工具型） |
|---------|---------------|---------------------|
| 目标用户 | 海量用户，陌生人交易 | 固定客户群体，熟人/半熟人交易 |
| 功能复杂度 | 功能全面，追求GMV | 聚焦核心流程，够用即可 |
| 用户体验 | 追求极致体验，高并发 | 简单易用，稳定可靠 |
| 运营成本 | 需要专业团队维护 | 个人/家人可维护 |
| 迭代速度 | 快速迭代，持续优化 | 按需迭代，不求完美 |

### 3.2 核心目标

**首要目标**：让客户能够通过小程序自主下单，无需通过微信聊天传达需求，店家能够在一个界面看到所有待发货订单。

**次要目标**：实现库存的在线管理，让客户下单前能看到库存状态；实现订单全流程追踪，客户可查看物流信息。

**加分目标**：积累销售数据，为进货决策提供参考。

### 3.3 项目边界

**明确不做**：

- 不追求大量用户获取，初期只服务现有客户群体
- 不开发复杂的营销功能（优惠券、拼团、秒杀等）
- 不对接第三方物流平台，物流采用固定选项+手动管理
- 不开发移动端管理App，Web端足以满足需求
- 不追求高并发性能，初期同时10人在线足够

**明确要做**：

- 完整的商品展示和搜索功能
- 便捷的下单和支付流程（微信支付）
- 清晰的订单管理界面
- 简单的物流选项配置
- 基础的库存管理

**已落地的基础设施**：

- GitHub Actions CI/CD 自动部署（代码推送 → 测试 → 构建镜像 → 服务器部署）
- 双子域名 HTTPS（shop.qianchengsuoju.cn + admin.qianchengsuoju.cn，Let's Encrypt 自动续期）
- admin 管理端 nginx Basic Auth 防护（用户名 malladmin）
- 钉钉告警：支付异常、退款异常实时通知
- 数据库每日自动备份（mysqldump 本地 + OSS 云端冷备）
- 订单15分钟超时自动取消 + 库存恢复

## 四、目标用户

### 4.1 C端用户（消费者）

**用户画像**：

- 画像A：家庭用户，年龄30-50岁，偶尔需要购买锁具或胶类进行家居维修，通过微信与店家联系，有时表达不准确导致沟通成本高
- 画像B：装修师傅，年龄25-45岁，长期从本店采购，有固定需求清单，希望快速下单不用反复确认
- 画像C：小型工程队负责人，采购量大，需要了解库存情况，希望能有批量下单功能

**使用场景**：

- 场景1：客户需要购买“防盗门锁”，通过小程序搜索“防盗门锁”找到商品，确认价格和库存后直接下单，无需打字沟通
- 场景2：老客户需要补货，直接在小程序下单，选择常用收货地址和物流方式，5分钟内完成下单
- 场景3：客户不确定买什么规格，在商品详情页查看详细参数，或联系店家咨询后下单

**核心需求**：快速找到商品、快速下单、支付便捷、可查看物流信息。

### 4.2 B端用户（运营人员）

**用户画像**：

- 主要用户：家人或店员，IT能力有限，更习惯图形界面操作
- 使用频率：每天早上来店里第一时间打开电脑查看当日订单

**使用场景**：

- 场景1：早上打开管理端仪表盘，一目了然看到今日新增订单数量、待发货订单列表
- 场景2：处理订单发货，选择物流、填写物流单号、标记已发货
- 场景3：客户电话咨询订单状态，在管理端快速查询订单状态并告知客户
- 场景4：商品到货后，在管理端更新商品库存数量

**核心需求**：一眼看清待办事项、操作简单直观、订单处理效率高。

## 五、解决方案

### 5.1 整体方案

开发一个小程序加Web管理端的商城系统：

**微信小程序（C端）**：

- 商品浏览：分类查看、关键词搜索、商品详情展示
- 购物车：加入购物车、修改数量、一键结算
- 下单支付：选择收货地址、选择物流方式、微信支付
- 订单管理：查看全部订单、订单详情、物流追踪
- 个人中心：收货地址管理、订单记录

**Web管理端（B端）**：

- 仪表盘：今日数据概览、最近订单列表、快捷入口
- 订单管理：订单列表、订单筛选、处理发货、填写物流
- 商品管理：商品列表、新增/编辑/删除、上下架、库存调整
- 物流管理：物流选项配置、启用/禁用
- 用户管理：查看用户列表

### 5.2 物流解决方案

考虑到店铺使用当地专线物流园的实际情况，物流功能采用简化方案：

**方案设计**：在管理端预先配置常用的5-10个物流选项（如德邦、顺心捷达、安能、专线A、专线B等），用户下单时只能从这些固定选项中选择。

**优势**：

- 开发成本低，无需对接物流API
- 运营成本低，无物流接口费用
- 管理简单，店家熟悉这些物流公司
- 满足实际需求，客户能清楚知道用什么物流发货

**劣势**：客户无法自定义物流，但这对实际运营影响不大。

### 5.3 技术方案

| 模块 | 技术选型 | 选择理由 |
|------|---------|---------|
| 后端框架 | Spring Boot + MyBatis-Plus | 成熟稳定，社区资源丰富 |
| 数据库 | MySQL 8.0 | 开源免费，关系型数据库适合业务场景 |
| 缓存 | Redis 7 | 登录限流、分布式锁 |
| 小程序 | uni-app | 一次开发多端，支持微信小程序 |
| 管理端 | Vue3 + Element Plus + Pinia | 组件丰富，状态管理清晰 |
| 部署 | Docker Compose + 云服务器 | 后端+管理端容器化，MySQL/Redis 宿主机直装（省内存） |
| CI/CD | GitHub Actions | 自动测试、构建镜像、SSH 部署 |
| 监控 | Spring Boot Actuator + Prometheus + 钉钉告警 | 健康检查、metrics、异常实时通知 |
| 备份 | mysqldump + OSS 冷备 + cron | 每日自动备份，30天保留 |

详细技术方案见《商城单体项目规划文档》。

## 六、价值分析

### 6.1 实用价值

| 改进项 | 当前状态 | 上线后 |
|-------|---------|--------|
| 客户下单方式 | 微信聊天，反复沟通确认 | 小程序自主下单，5分钟完成 |

**工程能力**：Git版本控制、Docker容器部署、Nginx反向代理、Linux服务器基础操作。

## 七、项目约束

### 7.1 技术约束

- 小程序仅支持微信小程序平台，暂不开发其他端
- 支付仅集成微信支付，暂不支持其他支付方式
- 管理端仅支持桌面端浏览器访问
- 系统设计考虑后期扩展，但不预置过多扩展功能

### 7.2 时间约束

- 开发周期约4个月（业余时间每天2-3小时），核心功能已基本完成
- 当前处于上线前准备阶段，等待 ICP 备案通过后部署生产环境

### 7.3 成本约束

- 年度运营成本控制在5400元以内（服务器+第三方服务+包装）
- 开发成本尽量降低（利用AI辅助开发，减少人力投入）
- 部署方案选用 2c2g 云服务器，MySQL/Redis 直装宿主机节省约 350MB 内存

### 7.4 运维约束

- 初期运维由本人负责，家人只需学习使用管理端
- 预留一定的学习成本让家人适应新系统
- 制定简单的异常处理流程应对系统故障
