# ADR-0009：图片对象回收以数据库引用为真相源，延迟回收并保留回收站

- 状态：Accepted
- 日期：2026-11-24
- 关联：Spec #88、PR #96、OSS 流量与容量治理、图片生命周期
- 取代：业务写入路径直接删除对象存储图片的做法（`SkuServiceImpl.deleteSku`）

## 背景

图片 URL 分散保存在四处：`spu.images`（JSON 数组）、`sku.image`、
`order_item.product_image` 和 `user.avatar_url`。其中 `order_item.product_image`
是下单瞬间写入的订单图片快照，历史订单详情依赖它。

现有代码没有统一的图片所有权模型，且两处方向相反：

- `deleteSku` 无条件删除 SKU 图片。SKU 图经常与 SPU 主图共用同一个 URL，
  删除一个 SKU 会连带删坏商品主图和其他 SKU 的图；
- `updateSpu` 覆盖 `images` 数组、`deleteSpu` 软删除、用户换头像，都不删除
  旧对象，对象只增不减。

Bucket 未开启版本控制，误删不可恢复。当前 1.32 GB 容量主要是种子商品的
1028 张原图，单张约 1.28 MB；容量问题目前不严重，但缺少回收机制会让对象
随运营时间无限增长。

## 决策

1. 数据库是图片引用的唯一真相源。引用集合取全表，不排除软删除记录：
   `spu.images`、`sku.image`、`order_item.product_image`、`user.avatar_url`。
2. 业务写入路径永不删除图片对象。删除 `deleteSku` 中的即时删除调用；
   删除图片对象只允许通过图片回收流程。
3. 图片回收采用延迟 mark-sweep：定期用“对象键集合减去引用集合”得到候选，
   再按宽限期筛选。URL 按路径部分映射为对象键，不依赖域名，避免将来切换
   自定义域名或 CDN 后把全部引用误判为外部图片。若本轮能映射到对象的引用
   数为零，整轮中止，不删除任何对象（失败关闭）。
4. 回收范围是白名单前缀 `products/`、`avatars/`、`banners/`；`trash/`
   永不参与扫描，其它前缀一律不碰。
5. 宽限期为 7 天，以对象最后修改时间计算。未满宽限期的对象即使没有引用
   也不回收，覆盖“已上传但尚未保存”的后台上传。
6. 回收先进入回收站：复制到 `trash/<yyyyMMdd>/<原对象键>` 后再删除原对象；
   `trash/` 保留 30 天后由每日任务物理删除。复制失败不得删除原对象。
7. 回收任务有 `off`、`report`、`trash` 三种模式，默认关闭。每周定时执行并
   使用分布式锁；首次上线先以 `report` 模式运行，确认报告与实际一致后再
   切换 `trash`。
8. 订单图片快照是永久强引用，不参与回收；只有订单记录本身被清理时才可能
   释放对应对象。
9. 列目录或复制失败时中止本轮，只记录日志；回收结果输出结构化日志，异常或
   单次回收量超过阈值时通过钉钉告警。
10. 暂不引入媒体表。若将来出现多 Bucket、CDN 域名切换、素材库或图片处理
    流水线，再评估 `media_object` 台账。

## 后果

- 孤儿图片最长会保留“宽限期 + 回收站保留期”，约 37 天；回收站期间存储
  短暂翻倍。
- 回收任务依赖 `ListObjects` 权限。本地环境已验证可用，生产环境需单独确认；
  权限不足时任务失败关闭，不会误删。
- 必须提供 `docs/image-gc-runbook.md` 运维手册，说明如何看报告、如何从回收站
  恢复单张图片、如何一键关闭回收。
- 以后新增任何保存图片 URL 的字段，都必须同步加入引用集合；这是本方案
  唯一需要人工维护的边界。
- 订单历史图片永不失效，代价是商品图即使商品已删除也不能释放。

## 备选方案

- 写时同步引用计数并立即删除：实时、无垃圾窗口，但要处理 JSON 数组、共用
  引用、上传未保存、软删恢复和并发，`deleteSku` 已经证明了它的失败模式，
  未采用。
- 永不删除、只做存储分层：零误删风险，但对象无上限增长，问题只是延后，
  未采用。
- 开启版本控制作为误删安全网：会改变全 Bucket 的删除语义并让历史版本持续
  占用容量，回收站更可控，未采用。
- 新建 `media_object` 台账：最规范，但要改上传链路和全部引用点，当前规模
  收益不足，未采用。
