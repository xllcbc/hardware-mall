# ADR-0005：取消后自动退款以支付记录为事实来源

- 状态：Accepted
- 日期：2026-11-11
- 关联 Spec：#50
- 关联 Issue：#52

## 背景

顾客在订单超时取消后仍完成微信支付时，旧实现会在支付事务内直接调用微信退款：

- 支付回调的 Ack 被秒级退款外呼阻塞，微信可能因超时重复回调。
- 微信已受理退款后，本地事务若提交失败，支付记录会回滚为已支付，与资金事实不一致。
- 退款接口不区分“已受理”“结果未知”“确定失败”，所有异常都停留在退款中。
- 告警按类型全局防抖，多笔订单同时失败时只能看到第一笔。
- 已取消订单的退款失败会尝试把订单改成 9，歪曲订单生命周期。

## 决策

1. **订单生命周期与退款事实分离。** 已取消订单的迟到支付退款不推进订单状态，订单始终保持“已取消”（5）。退款受理、结果未知和确定失败只记录在支付记录上；支付记录是退款事实的权威来源。
2. **自动退款在支付事务提交后执行。** 支付事务内只更新支付记录与订单状态；命中“订单已取消 + 支付成功”时发布 `LatePaymentRefundEvent`。监听器在 `AFTER_COMMIT` 通过有界线程池（核心 1、最大 2、队列 200，饱和时由调用线程执行并记录饱和日志）异步发起退款，支付回调立即 Ack。
3. **退款受理返回三态。** `ACCEPTED` 表示微信已受理；`UNKNOWN` 表示超时、网络异常、5xx、响应缺失或响应无法校验；`DEFINITE_FAILED` 表示请求未发出或微信明确返回 4xx 业务错误。判定保守：只有确定失败才回退。
4. **确定失败回退。** 支付记录 `REFUNDING → PAID`；订单仅在仍为“退款中”（6）时置为“退款失败”（9），已取消订单保持 5。结果未知保持“退款中”。
5. **告警按订单维度。** 退款结果未知、退款确定失败、退款对账回退和自动退款监听器异常都使用“类型 + 订单 ID”作为防抖 key，多笔订单不互相吞单；聚合告警仍按类型防抖。
6. **补偿由退款对账承担。** 监听器异常或任务丢失时支付记录保持已支付；退款对账扫描“退款中”记录和“已支付 + 订单已取消”记录，自动补发并收敛（见 Issue #53）。

## 后果

- 退款对账不能只扫描订单状态 6，必须以支付记录为入口，否则已取消订单的滞留退款无法收敛。
- 订单状态 9 只表达订单退款流程需要人工处理，不再表示已取消订单的退款结果。
- 自动退款的最终一致性依赖退款回调与退款对账；受理成功不等于退款完成。
- 有界线程池饱和时会退回支付回调线程执行，属于牺牲延迟换可靠性的降级路径，必须保留饱和日志。

## 备选方案

- **支付事务内同步调用微信退款**：继续占用数据库连接、阻塞回调 Ack，且本地提交失败会回滚已受理的退款状态，未采用。
- **所有退款异常都按确定失败回退**：响应丢失时微信可能已受理，回退会导致重复退款或错误的订单状态，未采用。
- **所有退款异常都保持退款中**：微信明确 4xx 拒绝时记录会永久滞留退款中，未采用。
- **按告警类型全局防抖**：多笔订单同时失败时只能看到第一笔，未采用。
