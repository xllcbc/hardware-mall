# ADR-0008：订单详情的支付状态同步归支付模块

- 状态：Accepted
- 日期：2026-11-23
- 关联 Epic：#77
- 关联 Issue：#80

## 背景

“支付记录已支付、订单仍待付款”的修复与“待支付时查询微信补单”曾同时存在两份：

- 订单门面的详情读路径在返回前内联修复订单状态，并直接外呼微信查单；
- 支付模块在支付成功处理里也按支付事实推进订单状态。

这带来三个问题：读接口会悄悄写订单；同一修复规则有两个所有者，容易漂移；订单查询（读模型）为了详情不得不接触支付网关与 Redis 去抖。支付与订单的耦合需要一个单一所有者。

## 决策

1. **支付模块是详情支付状态同步的唯一所有者。** `PayService` 提供同步入口 `syncPaymentStatus(orderId)`：30 秒内同一订单最多触发一次，去抖 key 保持 `lazysync:order:<orderId>`。
2. **同步内容不变。** 支付记录已支付且订单仍为待付款时，以条件更新把订单修复为待发货；支付记录待支付时查询微信，`tradeState=SUCCESS` 时走既有 `processPaymentSuccess`。自调用由 `TransactionTemplate` 提供事务，保持支付记录与订单状态同一原子单元。
3. **订单门面只做触发。** 详情路径负责归属校验，仅在订单为待付款时调用同步入口，再委托订单查询模块组装视图；同步异常由门面吞掉并记录告警日志，不影响详情返回。
4. **读模型保持只读。** 订单查询模块不依赖支付网关、不写订单；详情展示仍按订单读取最新支付记录。
5. **支付入口不变。** 支付回调、退款回调与退款对账的行为和入口保持原样，继续遵守 ADR-0005 的“退款事实以支付记录为权威”。

## 后果

- 详情读路径的唯一副作用收敛到支付模块，订单生命周期不再被读请求改写。
- 去抖、修复与查单补单只有一份实现；支付模块新增同步用例即可锁住回调丢失兜底。
- 同步入口抛出的异常必须由调用方决定是否忽略；详情路径必须吞掉，其他调用方需自行处理。
- 微信查询量维持原有 30 秒去抖上限，不因模块迁移放大。

## 备选方案

- **继续留在订单门面**：读接口继续写订单，且修复规则与支付模块重复，未采用。
- **改为异步任务或消息**：会让详情页的补单结果延迟，且引入新的投递与重试机制，超出本次边界，未采用。
- **支付模块与订单模块各保留一份修复**：所有者仍然不唯一，再次出现漂移风险，未采用。
