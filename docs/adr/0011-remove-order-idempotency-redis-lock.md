# ADR-0011：移除下单幂等的 Redis 短时锁

- 状态：Accepted
- 日期：2026-11-26
- 关联：Issue #101、#102、#104
- 取代：ADR-0006 的决策 2；ADR-0006 其余决策仍然有效

## 背景

ADR-0006 把下单幂等的权威迁移到数据库后，仍在数据库认领前增加了一把 300 秒
Redis 短时锁。实际代码无论是否取得该锁都会继续执行数据库认领，因此它没有保护
任何临界区，也没有实现 fast-fail：

- 同一幂等键是否重复下单，最终由 `order_idempotency` 的唯一键和状态机决定；
- 该锁每次下单增加一次 Redis 往返和一个故障点，却不减少数据库认领；
- 锁获取失败后仍走数据库，无法承诺“处理中”语义，文档却把它描述为防重防线；
- 当前低流量自用商城没有监控证据表明同一 `(user_id, idem_key)` 的并发认领是瓶颈。

这层锁的维护成本和叙述风险高于收益，故删除它及其持有者令牌的 Redis 释放逻辑。

## 决策

1. 下单认领直接进入数据库状态机，不再获取或释放 Redis 短时锁；数据库唯一键
   `(user_id, idem_key)` 与 `order_idempotency` 状态机是唯一幂等权威。
2. 持有者令牌保留，只用于幂等记录的数据库 CAS 更新；旧持有者不能覆盖新请求的记录。
3. 删除仅为该锁使用的 key 拼装、TTL 配置、裸 SETNX 和 Lua 比较删除逻辑。
4. 不修改数据库表结构、`X-Idempotency-Key` 请求头、业务错误码和既有重试语义。
5. 缓存重建与失效、批量回填、用户身份锁、定时任务等其他 Redis 锁保持不变。
6. 未来重新引入只允许“冷路径 fast-fail”形态：数据库优先，确认无记录后才抢锁；
   锁竞争返回明确的三态结果，获取后立即释放，并带竞争指标。不允许恢复当前
   “无论是否抢到锁都无条件执行数据库认领”的形态。

## 后果

- 下单链路少一次 Redis 往返和一个故障点，幂等正确性不再依赖 Redis 可用性。
- 幂等记录的状态机、请求指纹冲突检测、失败后重试和超时回收语义保持不变。
- 持有者令牌的生命周期只服务于数据库 CAS，不再与 Redis 锁绑定。
- 同一幂等键的高并发认领直接由数据库唯一约束收敛；若数据库唯一键冲突成为
  瓶颈，需要承担相应的数据库争用成本。

## 重新引入条件

只有监控同时证明以下两点，才重新评估冷路径 fast-fail 锁：

1. 同一个 `(user_id, idem_key)` 的并发争抢显著；
2. 数据库唯一键冲突已经影响下单吞吐或延迟，成为可测量的瓶颈。

重新引入前还必须明确三态结果、立即释放策略、指标与回滚方案，且不得削弱数据库
唯一键和状态机的最终守卫地位。

## 备选方案

- 保留现有 Redis 短时锁：未采用。它不保护临界区，不减少数据库认领，却增加网络
  往返和故障点。
- 用应用内互斥替代：未采用。只能覆盖单进程，无法提供跨实例的幂等保证。
- 继续用订单表唯一索引直接判重：未采用。无法表达“处理中”和“失败可重试”，
  也无法区分同键不同载荷。
