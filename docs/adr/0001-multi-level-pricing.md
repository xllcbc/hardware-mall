# ADR-0001：多级用户定价采用零售基价与等级分类倍率

- 状态：Accepted
- 日期：2026-10-29
- 关联设计：`docs/多级用户定价设计文档.md`
- 关联交付计划：`docs/多级用户定价交付更新计划.md`

## 背景

系统原先只有零售价和 SKU 级批发价两档。实际业务需要多个用户等级，并且同一等级在不同商品分类下适用不同折扣。继续为每个等级在 SKU 上增加价格列会造成字段膨胀、维护困难，也无法清晰表达分类维度。

## 决策

1. `sku.price` 是唯一零售基价。
2. 用户通过 `user_level` 归属一个等级。
3. 非零售等级的折扣由 `level_category_discount` 的等级分类矩阵表达。
4. 成交单价由纯函数按“零售基价 × 倍率”计算，单位价四舍五入保留两位，再乘数量。
5. 商品缓存只保存零售区间和商品级折扣开关，不保存任何等级的最终价格。
6. 倍率缓存独立于商品缓存；倍率变更在数据库事务提交后失效定价缓存，不失效商品缓存。
   失效锁等待和 TTL 上限见 ADR-0002。
7. 订单在下单瞬间保存等级 ID、等级名称和倍率快照。
8. 商品级 `exclude_discount` 对所有等级生效，不引入 SKU 级例外。

## 后果

- 新增等级只需要维护等级分类矩阵，不需要给每个 SKU 增加价格字段。
- 商品列表和详情可以复用同一份中性缓存，再按当前等级实时裁剪。
- 订单金额和等级快照不受后续倍率修改影响。
- 管理端必须显式区分“倍率缺口”和“显式配置 1.0000”。
- 历史 `order_item.price_type` 不再作为新订单定价依据；历史订单快照字段可以为空。
- 需要一次数据库迁移、真实 MySQL 验证和旧缓存清理。
- 定价缓存失效失败最长由 ADR-0002 定义的 300 秒 TTL 兜底。

## 备选方案

- 每个等级在 SKU 上存一份绝对价格：字段膨胀，难以扩展，未采用。
- 等级系数与分类系数相乘：无法表达每个等级分类组合的独立配置，未采用。
- 将等级最终价格写入商品缓存：缓存键会按等级膨胀，且倍率变化需要失效商品缓存，未采用。
- SKU 级折扣例外：维护成本高，与商品级固定控价需求不匹配，未采用。
