# ADR-0006：下单幂等以数据库记录为权威，Redis 仅作快锁

- 状态：Accepted
- 日期：2026-11-11
- 关联：Epic #50、Issue #55
- 取代：以 5 分钟 Redis 占坑作为唯一下单幂等保护的旧实现

## 背景

旧实现只在 Redis 写入 5 分钟占位键：

- 订单已创建但响应丢失时，顾客重试只能看到“请勿重复下单”，拿不到原订单；
- 占用键过期或 Redis 重启后，同一幂等键可以创建第二笔订单；
- 删除键不校验持有者，旧请求可能误删新请求的锁；
- 业务失败时无法区分“可重试”与“已成功”，也无法按请求内容识别冲突。

订单创建是数据库事实，幂等判断也必须在数据库中有持久、可并发安全认领的记录。

## 决策

1. 新增 `order_idempotency` 表，保存用户、幂等键、请求指纹、状态
   （`PROCESSING` / `SUCCEEDED` / `FAILED`）、持有者令牌和订单 ID；
   `(user_id, idem_key)` 唯一键是并发下的最终守卫。
2. Redis 只作 300 秒快锁，key 包含用户 ID，值为本次请求的 ownerToken。
   Redis 异常或快锁未获取时继续走数据库，数据库保证不重复下单。
3. 同一用户、同一幂等键：
   - 已成功且请求指纹相同：返回原订单，不创建第二笔；
   - 已成功但请求指纹不同：冲突，提示刷新；
   - 处理中且未超时：明确提示“处理中”；
   - 失败：允许同一幂等键重新认领。
4. 请求指纹覆盖商品项（SKU + 数量，按 SKU 排序）、地址、物流、买家备注和
   期望支付金额。
5. 订单创建与幂等记录置为 `SUCCEEDED + order_id` 在同一数据库事务完成；
   事务内更新失败则回滚订单。提交前失败用独立事务置为 `FAILED`。
6. 订单 VO 组装在事务提交之后、失败释放范围之外；VO 组装失败不得释放或
   改写已成功的幂等记录，重试仍返回原订单。
7. Redis 释放使用 Lua 比较并删除；数据库更新均带 ownerToken 条件。旧持有者
   不能删除或覆盖新请求的锁和幂等记录。
8. 处理中超过 10 分钟回收为失败；成功/失败记录保留 7 天后清理。
9. 迁移先于应用发布；完整建表脚本、测试 schema、增量迁移和发布 verify 保持
   一致。旧应用不引用新表，应用回滚不需要删表。

## 后果

- 幂等判断不再依赖 Redis 可用性，Redis 过期或重启不会产生重复订单。
- 响应丢失后，客户端用相同幂等键与相同载荷重试可以拿回原订单。
- 幂等表会持续增长，必须保留回收与清理任务；处理中记录的宽限时间必须大于
  正常下单耗时。
- 客户端在载荷变化或收到冲突提示后必须重新获取幂等键；成功后清空，失败保留。

## 备选方案

- 继续只使用 Redis 占坑：无法在过期或重启后保证幂等，也拿不回原订单，未采用。
- 以订单表唯一索引直接判重：无法保存“处理中”和“失败可重试”两种瞬时状态，
  也无法区分同键不同载荷，未采用。
- 只用数据库行锁串行化所有下单：锁粒度大、跨请求不可控，且不能表达重试语义，
  未采用。
