# 图片回收运维手册

> 适用对象：运维、后端值班。关联决策：ADR-0009「图片对象回收以数据库引用为真相源，延迟回收并保留回收站」（ADR 尚未合入本仓库，决策背景见图片生命周期治理 spec 与 `CONTEXT.md` 的「图片回收」「回收站」词条）。
> 相关代码：`ImageGcJob`（每周回收）、`ImageTrashPurgeJob`（每日回收站清理）、`ImageTrashRestoreRunner`（单张恢复）。

图片回收以数据库为唯一真相源，只处理 `products/`、`avatars/`、`banners/` 三个白名单前缀下、超过宽限期且零引用的孤儿对象。业务写入路径不再删除图片对象，图片回收是唯一的删除入口。

## 1. 三种模式

`IMAGE_GC_MODE` 决定任务行为，**默认 `off`**：

| 模式 | 每周回收任务（周一 03:00） | 每日回收站清理（03:40） | 用途 |
|------|---------------------------|------------------------|------|
| `off` | 不列目录、不读库，直接跳过 | 不列目录、不删除，直接跳过 | 默认态；出现异常时一键止损 |
| `report` | 只输出报告，不复制、不删除 | **不执行**（报告模式不做任何物理删除） | 首次上线观察两周 |
| `trash` | 孤儿对象复制到 `trash/<yyyyMMdd>/<原对象键>`，复制成功后才删除原对象 | 删除路径日期超过保留期（默认 30 天）的回收站副本 | 正式回收 |

三种模式都要求多实例部署时拿到 Redis 分布式锁才执行：`job:image-gc`、`job:image-trash-purge`。拿不到锁的实例直接跳过，不会重复复制或删除。

## 2. 配置项

全部通过环境变量注入，修改后需要重启后端容器生效：

| 环境变量 | 默认值 | 说明 |
|----------|--------|------|
| `IMAGE_GC_MODE` | `off` | `off` / `report` / `trash` |
| `IMAGE_GC_GRACE_DAYS` | `7` | 宽限期：对象最后修改时间早于「当前时间减该天数」才可能成为候选 |
| `IMAGE_GC_TRASH_RETENTION_DAYS` | `30` | 回收站保留天数，只按回收路径中的批次日期判断 |
| `IMAGE_GC_ALERT_MAX_BYTES` | `209715200`（200 MB） | 单轮回收/清理字节数告警阈值，`<=0` 关闭该维度 |
| `IMAGE_GC_ALERT_MAX_COUNT` | `200` | 单轮回收/清理对象数告警阈值，`<=0` 关闭该维度 |
| `IMAGE_GC_REPORT_CRON` | `0 0 3 * * MON` | 每周回收任务 cron |
| `IMAGE_GC_PURGE_CRON` | `0 40 3 * * *` | 每日回收站清理 cron |
| `IMAGE_GC_RESTORE_OBJECT_KEY` | 空 | 一次性单张恢复；恢复完成后必须移除 |
| `DINGTALK_WEBHOOK` / `DINGTALK_SECRET` | 空 | 未配置时告警静默跳过，任务本身不受影响 |

## 3. 首次开启：先跑 `report`

1. 确认业务侧已不再删除图片对象（P0 已上线），且 `OSS_ACCESS_KEY` 具备白名单前缀的 `ListObjects` / `CopyObject` / `DeleteObject` 权限。权限不足或配置错误时任务会失败关闭，不会批量删除。
2. 在部署配置中设置 `IMAGE_GC_MODE=report`，重启后端。
3. 等待下一次周一 03:00，或临时把 `IMAGE_GC_REPORT_CRON` 改成近几分钟并重启，手动触发一轮。
4. 连续两周核对报告（见第 4 节）；确认「候选对象」与直觉一致、`aborted=false` 后再考虑切 `trash`。
5. 切 `IMAGE_GC_MODE=trash` 并重启。首轮建议把 `IMAGE_GC_ALERT_MAX_BYTES` / `IMAGE_GC_ALERT_MAX_COUNT` 调低，确保回收量异常时能收到告警。

## 4. 如何阅读报告

报告通过结构化日志输出（无 HTTP 接口），默认日志级别下可直接检索：

```bash
docker compose logs backend | grep -E "图片回收报告|图片回收中止"
```

`图片回收报告: {json}` 中字段含义：

| 字段 | 含义 |
|------|------|
| `executed` | 是否真正执行；`mode=off` 为 `false` |
| `mode` | 本轮模式 |
| `aborted` / `abortReason` | 是否中止及原因；中止时未复制、未删除任何对象 |
| `scannedObjectCount` | 白名单前缀下扫描到的对象数 |
| `mappedReferenceCount` | 数据库引用成功换算为对象键的数量（重复引用重复计数） |
| `referencedObjectCount` | 被至少一个引用指向的扫描对象数 |
| `unreferencedObjectCount` | 零引用对象数（含仍在宽限期内的对象） |
| `candidateCount` | 超过宽限期且零引用的候选对象数 |
| `reclaimableBytes` | 候选对象可回收字节数 |
| `sampleObjectKeys` | 候选对象键样例（排序后最多 20 条） |
| `trashedObjectCount` / `trashedBytes` | `trash` 模式本轮成功移入回收站的数量与字节数 |
| `trashFailedObjectCount` | 复制或删除失败、原对象因此保留的数量 |

判读要点：

- `aborted=true`：先看 `abortReason`。列目录失败、数据库读取失败、映射到的引用数为零时会整轮中止，此时**没有任何删除**，修好配置/权限后重跑即可。
- `mappedReferenceCount=0`：通常意味着数据库读不到图片或 URL 无法换算成对象键，属于保护性中止，不要绕过。
- 报告只提供样例，核对个别对象时可在 OSS 控制台按 `sampleObjectKeys` 搜索；也可以直接看数据库中的引用字段。

## 5. 回收站与每日清理

`trash` 模式把对象复制到 `trash/<yyyyMMdd>/<原对象键>`，例如：

```text
products/2026/11/a.jpg  ->  trash/20261124/products/2026/11/a.jpg
```

每日清理任务（默认 03:40）只删除**路径日期**超过保留期的副本：

- 距今 31 天及以上：删除；
- 距今 30 天及以内：保留（「超过保留期」才删除）；
- 路径不符合 `trash/<yyyyMMdd>/...` 布局或日期非法：跳过并记 `warn`，永不删除。

是否过期**不看对象最后修改时间**，复制动作改变 `Last-Modified` 不会延长或缩短保留期。

清理只在 `trash` 模式执行：`report` 模式保持只读、不做任何物理删除，`off` 模式作为一键止损也不删除。因此从 `trash` 切走期间已过期的副本会暂存，切回 `trash` 后的下一轮按同一日期规则补删。

日志：

```bash
docker compose logs backend | grep -E "回收站保留期清理"
```

- `回收站保留期清理完成: listed=..., expired=..., deleted=..., deletedBytes=..., failed=..., skipped=..., retentionDays=...`
- 列目录失败会整轮中止并告警 `IMAGE_TRASH_PURGE_FAILED`。
- 单个对象删除失败会继续处理其他对象，失败对象保留到下一轮重试，并告警 `IMAGE_TRASH_PURGE_FAILED`。任务可幂等重跑：重跑只按同一日期规则重新判断，未过期对象不会被删除。

## 6. 从回收站恢复单张图片

1. 从日志的 `sampleObjectKeys` 或 OSS 控制台的 `trash/` 目录找到完整回收站对象键，例如 `trash/20261124/products/2026/11/a.jpg`。
2. 在部署配置中添加（只加一次，不要长期保留）：
   ```bash
   IMAGE_GC_RESTORE_OBJECT_KEY=trash/20261124/products/2026/11/a.jpg
   ```
3. 重启后端一次。启动器会把副本复制回原对象键，校验可访问后删除回收站副本。
4. 确认日志出现 `已从回收站恢复图片: trash/... -> products/...` 后，**移除该环境变量并再次重启**，避免每次启动重复恢复。
5. 浏览器/小程序仍显示破图时，先确认数据库引用字段仍指向原对象键，再排除 CDN/浏览器缓存。

失败行为：对象键不合法、副本已不存在（可能已恢复过）、复制失败或恢复后不可访问时返回失败并保留回收站副本；查看 `从回收站恢复图片失败` / `恢复跳过` 日志。恢复不会修改数据库。

## 7. 告警与响应

| 告警类型 | 触发条件 | 处置 |
|----------|----------|------|
| `IMAGE_GC_ABORTED` | 每周回收中止 | 看 `abortReason`；权限/数据库问题修好后等待下一轮或临时改 cron 重跑 |
| `IMAGE_GC_FAILED` | 每周回收任务抛异常 | 查看后端堆栈；任务不会向调度线程抛出 |
| `IMAGE_GC_THRESHOLD` | 单轮移入回收站的对象数或字节数超阈值 | 核对报告样例与数据库引用；疑似误判立即切 `off` |
| `IMAGE_TRASH_PURGE_FAILED` | 回收站清理中止、部分删除失败或任务异常 | 权限/网络修复后下一轮自动重试；确认失败对象仍在回收站 |
| `IMAGE_TRASH_PURGE_THRESHOLD` | 单轮永久删除量超阈值 | 确认保留期配置是否被改小；必要时切 `off` 阻止继续清理 |

阈值告警只提示「本轮删除量异常」，删除已经发生；真正的止损手段是切换模式。

## 8. 一键关闭

异常时立即执行：

1. 将 `IMAGE_GC_MODE=off`（不要改成 `report`——`report` 仍会继续只读扫描与告警）。
2. 重启后端容器使配置生效。
3. 确认日志出现 `图片回收任务未启用(mode=OFF)` 与 `回收站保留期清理跳过(mode=OFF)`，此后不再产生任何复制或删除。

`off` 只影响后续任务轮次：已经在执行的一轮不会被打断，等它结束即可（最长为一轮扫描时间）。恢复站点的历史副本不会被自动删除，可继续按第 6 节恢复。

## 9. 故障关闭行为速查

| 场景 | 行为 |
|------|------|
| 列目录失败 / 权限不足 | 整轮中止，不复制、不删除 |
| 数据库引用读取失败 | 整轮中止，不删除 |
| 本轮映射到的引用数为零 | 整轮中止，不删除 |
| 复制到回收站失败 | 中止本轮，当前及后续原对象全部保留 |
| 删除原对象失败 | 中止本轮，回收站副本与原对象都在，下一轮重新评估 |
| 回收站清理列目录失败 | 整轮中止，不删除 |
| 回收站清理单对象删除失败 | 继续处理其他对象，失败对象下一轮重试 |
| 未配置钉钉 webhook | 告警静默跳过，任务正常执行 |
| 多实例同时触发 | 只有拿到锁的实例执行 |
