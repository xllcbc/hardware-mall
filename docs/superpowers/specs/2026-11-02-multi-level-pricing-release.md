# 多级用户定价发布收口规格

日期：2026-11-02
状态：已发布为父 Issue #13（2026-11-04 修订：暂缓定价缓存专属监控）

## Problem Statement

五金商城已经具备多级用户定价的主要实现，但管理员和用户仍不能安全地把它当作正式能力使用。迁移脚本同时承担扩展和收缩，无法证明真实 MySQL 上的升级结果；等级分类倍率变更在缓存失效失败后会继续暴露旧价格；批量 SKU 配置在事务提交前操作缓存；新增分类后倍率缺口和复制矩阵的语义没有完全收口；管理端价格视角仍停留在原型，缺少正式验收。

现有实现分散在多个历史分支和 ticket 中，原型代码、旧批发价模型、正式定价模型与发布文档同时存在，容易被误认为已经完成。发布负责人无法确认哪一份实现可复用、哪一套迁移可执行、哪些 ticket 已验收，也无法在一次性发布前证明商品、购物车、订单和管理端使用的是同一套等级结算价。

## Solution

把已验证的多级用户定价实现收敛到一个受控发布分支，并从最新 `origin/main` 建立新的干净发布面。新分支通过 squash 导入已验证集成树，保留旧分支和原型作为只读归档，再按四组收口工作完成数据库迁移、定价与缓存边界、商品与订单链路、管理端正式视图。

最终只进行一次 PR、一次维护窗口发布和一次回滚演练。发布前使用 production schema 快照和隔离的 MySQL 8、Redis 7 环境完成自动化与浏览器验收；发布中使用停写、全库备份、schema preflight、迁移、部署、缓存清理和冒烟门禁；发布后继续跟踪错误日志和价格一致性。

## User Stories

1. 作为商城管理员，我希望创建和排序非零售等级，以便按不同客户群体配置价格。
2. 作为商城管理员，我希望新等级默认停用，以便在矩阵补齐前不会影响真实成交。
3. 作为商城管理员，我希望在启用等级前看到倍率缺口，以便补齐所有当前分类。
4. 作为商城管理员，我希望区分“倍率缺口”和显式配置的 `1.0000`，以便知道价格是兜底还是主动配置。
5. 作为商城管理员，我希望新增分类后看到已有启用等级出现缺口，以便及时补充倍率。
6. 作为商城管理员，我希望缺口在结算时按零售倍率兜底，以便商品在配置完成前仍能安全销售。
7. 作为商城管理员，我希望已启用等级不能复制不完整矩阵，以便不绕过启用完整性约束。
8. 作为商城管理员，我希望复制矩阵时保留来源等级的缺口，以便目标等级不会出现伪造的显式配置。
9. 作为商城管理员，我希望在保存、填充和复制矩阵前看到用户数、分类数和来源等级，以便确认影响面。
10. 作为商城管理员，我希望取消影响确认时不发生任何写请求，以便避免误操作。
11. 作为商城管理员，我希望给商品设置不参与折扣，以便固定控价商品对所有等级都使用零售基价。
12. 作为商城管理员，我希望把用户分配到用户等级，并让等级变更立即影响下一次登录后的价格视角，以便价格身份可控。
13. 作为商城管理员，我希望按用户等级筛选归属用户，并支持 URL 深链，以便从等级页面直接定位客户。
14. 作为商城管理员，我希望在现有商品管理页切换零售视角和启用等级视角，以便不离开日常工作流就能核对价格。
15. 作为商城管理员，我希望商品列表同时展示零售区间、等级结算区间、倍率、缺口和折扣开关状态，以便快速发现异常。
16. 作为商城管理员，我希望商品和用户页默认使用紧凑表格，并保留完整字段切换，以便约 1280px 视口下无需横向滚动。
17. 作为商城管理员，我希望图标操作具有 Tooltip、键盘焦点和可访问名称，以便高效且安全地完成日常操作。
18. 作为访客，我希望商品列表和详情始终显示零售基价，以便未登录时也能正常浏览。
19. 作为零售用户，我希望商品、购物车和订单都按零售基价结算，以便价格与我的等级身份一致。
20. 作为非零售等级用户，我希望商品列表区间、详情价格、购物车小计和订单金额都使用同一等级分类倍率，以便结算前看到的金额与最终支付一致。
21. 作为非零售等级用户，我希望等级名称、倍率和划线价不出现在用户端，以便界面只表达我实际能获得的价格。
22. 作为非零售等级用户，我希望倍率缺口时按零售基价展示，以便配置缺失不会导致错误低价。
23. 作为购买不参与折扣商品的非零售用户，我希望仍按零售基价结算，以便商品级控价规则优先于等级倍率。
24. 作为下单用户，我希望订单保存下单瞬间的等级名称、等级 ID 和倍率快照，以便后续等级或倍率修改不会改变既有订单。
25. 作为登录用户，我希望等级变更后旧 Token 失效，以便重新登录后使用新的价格身份。
26. 作为后台操作员，我希望倍率修改正常时在事务提交后立即生效，失败时由有界 TTL 兜底，最长不陈旧超过五分钟，以便价格调整不会长期滞留。
27. 作为后台操作员，我希望缓存失效失败时留下日志并由 TTL 兜底，以便不引入额外监控组件也能恢复。
28. 作为商品管理员，我希望批量保存 SKU 配置和库存时，数据库回滚不会留下错误 Redis 值，以便缓存始终服从已提交数据。
29. 作为发布负责人，我希望发布迁移只接受 production 原始 schema，并在发现旧批发价模型时中止，以便不会误跑未验证的兼容分支。
30. 作为发布负责人，我希望迁移前自动检查数据库结构并保留全库备份，以便迁移失败时可以恢复。
31. 作为发布负责人，我希望在隔离预发布环境使用 production schema 和脱敏数据验证迁移、商品价格、购物车和订单，以便不在生产首次试跑。
32. 作为发布负责人，我希望看到 PR CI、真实 MySQL、真实 Redis、管理端构建、小程序构建和浏览器验收全部通过，以便合并 main 前有统一门禁。
33. 作为测试工程师，我希望验收场景只通过公开发布行为断言价格和缓存结果，以便测试不会绑死内部 Service 调用方式。
34. 作为开发工程师，我希望旧分支和原型有明确归档标签，并只保留一个活跃发布 worktree，以便不会继续在十个分支间混用实现。
35. 作为开发工程师，我希望旧批发价设计明确标记为废案，以便后续人员不会把两档批发价重新当作备选方案。
36. 作为运维工程师，我希望一次维护窗口完成停写、迁移、部署、缓存清理和冒烟，以便发布顺序可执行、可回滚。
37. 作为运维工程师，我希望发布失败时能够恢复数据库备份并回滚上一版镜像，以便价格功能不会长期不可用。
38. 作为项目维护者，我希望 Issue #5-#11 在 CI、预发布和生产验收前保持开放，以便归档代码不会被误认为 ticket 已完成。

## Implementation Decisions

### Release Control

- 从操作时最新的 `origin/main` 创建 ASCII 分支 `codex/new-pricing-release`。
- 将已验证的定价集成树 squash 成发布分支的种子提交。旧集成分支和 Issue #11 原型继续保留原始历史，但不再作为开发基线。
- 为集成树和原型创建 annotated archive tag，并推送到远端后核对 SHA。
- 旧 worktree 在新分支完成构建和迁移测试前只读保留；验证通过后只保留一个活跃开发 worktree。
- 四个阶段是同一发布分支内的四组收口提交，不是四次独立部署。
- 发布采用一次 PR 和一次维护窗口。停写、备份、迁移、部署和回滚属于发布门禁，不使用“零停机”表述。

### Domain and Matrix

- `sku.price` 是唯一零售基价。
- 用户等级是用户同一时间唯一所属的定价群体。零售等级固定存在、固定启用，不可改名、停用或删除。
- 非零售等级的等级分类倍率采用等级与分类的完整矩阵表达，格子互不推导。
- 等级结算价按零售基价乘倍率计算，单价先按人民币两位小数四舍五入，再乘数量。
- `exclude_discount` 是商品级开关。开启后，所有用户等级都使用零售基价。
- 倍率缺口和显式 `1.0000` 在成交价格上相同，但管理语义不同。缺口必须继续显示为“未配置，零售兜底”。
- 新增分类后，已有启用等级允许出现新的倍率缺口，运行时按零售倍率兜底，不自动补写显式 `1.0000`。
- 启用等级前必须满足当前矩阵完整性。复制不完整矩阵到已启用等级必须拒绝，目标等级应先停用或补齐。
- 已创建订单的等级 ID、等级名称和倍率快照不得随后续等级或倍率修改而变化。

### Data and Migration

- 最终 schema 包含用户等级、等级分类倍率、用户当前等级、商品折扣开关和订单等级快照。
- 旧批发价模型是废案。production 从未启用双价格模型，因此不执行旧绝对批发价到分类倍率的数据转换。
- 发布迁移只接受 production 原始 schema。执行前检查旧批发价字段，发现旧结构时中止并要求人工处理。
- 新库初始化结构和发布迁移都落到同一最终模型。
- 发布前保存可校验的全库备份。迁移失败或严重回归时恢复备份并部署上一版镜像。
- 真实 MySQL 迁移测试必须覆盖表、字段、索引、唯一约束、零售等级、默认用户等级归属和订单快照列。

### Pricing and Identity

- 定价入口拆分为纯价格计算和带缓存、事务语义的定价规则读取。
- 用户身份继续通过 JWT 承载等级 ID。普通用户 Token 缺少等级 ID 时返回未认证，管理员 Token 不受等级限制。
- 商品列表、商品详情、购物车和订单都复用同一等级结算价口径。
- 商品列表区间价按零售基价区间乘同一个等级分类倍率计算，保证列表与详情一致。
- 商品缓存保持中性，只保存公共商品字段、零售价区间和折扣开关，不保存任何等级最终价格。
- 用户修改等级后，失效该用户全部 Token；等级未变化时仍允许管理员重试 Token 失效。

### Cache Consistency

- 定价缓存按用户等级保存分类倍率，不失效中性商品缓存。
- 矩阵保存、填充、复制以及等级启用、停用、删除必须在数据库事务提交后触发缓存失效。
- 当前规模不引入缓存失效 outbox，也不建设定价缓存专属指标和告警。事务提交后立即尝试失效，失败只记录日志。
- 缓存失效与重建使用同一把锁并设置有限等待；超时后失效请求立即返回，重建请求直接回源且不写缓存。
- 定价缓存使用 240 秒基础 TTL 和 0 至 60 秒抖动，最长陈旧时间不超过 300 秒。
- 价格相关商品缓存（`sku:info`、商品列表、详情、推荐和搜索）使用与定价缓存相同的 240 秒基础 TTL 和 0 至 60 秒抖动，最长陈旧时间不超过 300 秒。
- 商品列表、详情、推荐和搜索的缓存重建锁等待设置可配置上限，默认 500ms；超时后直接回源且不写缓存。
- 商品和批量 SKU 的缓存处理不得在数据库事务提交前删除缓存或写入库存缓存。
- 批量 SKU 获取拿到锁后再次批量读取缓存，只回源仍然缺失的 SKU；抢锁超时可退化为直接查库，但不得写缓存。
- 库存缓存读取、批量补齐和失效使用按 SKU 的同一把锁；未命中读取采用有界 singleflight，失效使用带锁删除。
- 库存缓存采用提交后失效和读取回源；数据库原子扣减仍是超卖判断的最终事实来源。
- 商品缓存失效失败记录 Micrometer 指标和告警，不引入 outbox。
- 缓存失效失败必须保留日志，并由最长 300 秒的 TTL 兜底。

### Interfaces and UI

- 用户等级、等级状态、等级分类倍率、矩阵填充、矩阵复制和商品价格预览通过管理端接口提供。
- 用户管理支持按等级过滤，用户等级筛选可从 URL 深链初始化。
- 商品管理新增只读价格视角，支持零售视角和启用等级视角，并返回零售区间、等级结算区间、倍率、缺口和折扣开关状态。
- 正式管理端复用现有商品页和用户页，不新建独立商品页或客户页。
- 用户等级页作为进入当前等级商品价格视图和归属用户的入口。
- 保存、填充和复制倍率前展示影响确认。取消确认不调用写接口。
- 商品和用户页默认使用紧凑视图，并提供完整字段切换。约 1280px 视口下默认视图不得横向滚动。
- 原型 mock、原型路由、条件加载和开发环境免登录旁路不得进入正式实现。
- 用户端不展示等级名称、倍率、划线价或价格性质标签，也不在小程序重新计算倍率。

### Documentation and Delivery

- 更新领域词汇，明确“倍率缺口”和“废弃批发价模型”。
- 新增 ADR 记录倍率缺口、启用等级复制限制、提交后直接失效和五分钟有界陈旧时间。
- 新增 ADR 记录价格相关商品缓存、库存缓存和批量 SKU 的新鲜度、有界锁等待与 singleflight。
- 现有多级用户定价 ADR 保留，并关联新的缓存失败语义。
- 旧批发价设计与旧批发价实施计划标记为 Superseded，明确是废案，仅用于历史追溯。
- 更新交付计划，使其与分支、迁移、缓存、测试和一次性发布决策一致。
- Issue #4 保持关闭；Issue #5-#11 只有在自动化、预发布和生产门禁通过后才能关闭。

## Testing Decisions

测试只断言外部可观察行为：数据库最终结构、HTTP 价格结果、订单快照、缓存失效与 TTL、管理端与用户端可见行为。测试不应依赖私有方法调用次数，也不应把 H2 的近似行为当作 MySQL 验收。

### Database Migration Seam

- 使用真实 MySQL 8 从 production 原始 schema 快照启动测试容器。
- 执行发布迁移，验证最终 schema、索引、唯一约束和默认零售等级。
- 验证 migration preflight 在发现旧批发价结构时中止。
- 验证迁移不会写入任何伪造的等级分类倍率。
- 参考现有 Mapper 集成测试的真实数据库断言方式，补齐 Testcontainers 使用模式。

### Backend Application Seam

- 启动真实 MySQL 8、Redis 7 和 Spring Boot HTTP 应用。
- 验证访客、零售用户、不同非零售等级、倍率缺口、显式 `1.0000` 和不参与折扣商品的价格。
- 验证商品列表、详情、购物车、订单创建和支付前金额一致。
- 验证订单等级快照在倍率修改后保持不变。
- 验证等级变更导致旧 Token 失效，管理员身份不携带用户等级。
- 验证矩阵保存、填充、复制在事务提交后失效定价缓存，回滚不产生 Redis 副作用。
- 模拟真实 Redis 锁超时，验证请求不会被无限阻塞、缓存 key 的保留行为以及五分钟 TTL 上限。
- 验证批量 SKU 配置回滚不写入库存缓存，提交后缓存回源得到已提交数据。
- 验证库存失效与重建并发时旧库存不会被写回，多个未命中请求不会同时回源。
- 验证批量 SKU 拿锁后 double-check、锁超时直接回源且不写缓存。
- 验证价格相关商品缓存最长不超过 300 秒，商品查询锁等待不超过配置上限。
- 验证商品缓存失效失败记录指标和告警。
- 复用现有控制器测试的接口契约和 Redis 集成测试的真实连接方式，但新增测试必须在真实数据库事务中提交。

### Client Acceptance Seam

- 在隔离预发布环境启动正式管理端和 uni-app H5。
- 验证价格视角切换、分类和关键词服务端筛选、用户等级深链和矩阵影响确认。
- 验证倍率缺口、显式 `1.0000` 和不参与折扣的文案差异。
- 验证取消确认不会发起写请求。
- 验证约 1280px 视口下默认商品页和用户页无横向滚动，完整字段切换保留全部列。
- 验证图标操作具备 Tooltip、键盘焦点和可访问名称。
- 验证用户端价格展示不含等级名称、倍率、划线价和批发标签。
- 微信小程序执行生产构建，并使用体验版人工验证首屏价格、购物车和下单。

### CI and Release Gates

- 提前创建 PR，使后端、管理端和小程序 CI 在合并前运行。
- 后端 CI 区分快速 H2 单元测试和真实 MySQL、Redis 验收测试。
- 迁移测试、真实 Redis 失效、浏览器验收和管理端、小程序构建均作为合并门禁。
