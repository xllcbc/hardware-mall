## 三、修复计划

### Phase 1 — 高危 6 项

#### H1 取消订单竞态资损 ✅ 已完成（commit `a51c885`）

**目标**：`OrderServiceImpl.cancelOrder` / `autoCancelOrder`

**改动**：
- 将"查状态 → 还库存 → 无条件 updateById"改为：CAS `WHERE id=? AND status=1` 条件更新
- `affected==0` 则抛异常使整个事务回滚，与同文件 `confirmReceive` 的既有 CAS 风格对齐
- 库存恢复移到 CAS 成功之后，避免"还了库存但订单没取消"的问题
- `autoCancelOrder` 同型改造，`affected==0` 返回 false

**验证**：编译通过；OrderServiceImplTest 的 Mockito 插件初始化问题是环境配置问题，与本次修改无关

**概念**：TOCTOU（Time-of-check to time-of-use）竞态。`@Transactional` 只保证单条语句原子，不保证"检查过的条件一直成立"。`updateById` 生成的 SQL 是 `WHERE id=?`（无 status 条件），会把并发者刚写入的状态覆盖掉。修复模式：把检查焊进 SQL 的 WHERE（CAS），失败抛异常掀桌子回滚。详见附录 A。

#### H2 封禁失效 + refresh 链路 ✅ 已完成（commit `34cd1fa`）

**目标**：`UserServiceImpl` + `UserController` + `AdminAuthController`

**改动**：
- `login()`：已存在用户若 `status==DISABLED` 抛 `BusinessException("账号已被禁用")`
- `refreshToken(userId, oldToken)`：校验用户状态、claims 补 `role`、新 token `sAdd` 登记、旧 token `sRemove` + 拉黑（带 TTL）
- `UserController.refresh` 从 Authorization header 解出旧 token 传入
- `updateUserStatus` 加管理员守卫：`role==ADMIN` 抛 `BusinessException("管理员账号不允许封禁")`
- `AdminAuthController` **移除** admin token 登记（admin 不参与封禁登记，refresh 仅保留旧 token 拉黑）
- `updateUserStatus` 拉黑补 TTL（修复内存泄漏）

**设计决策**：封禁能力收敛为用户侧专属。管理后台用户列表里管理员行点禁用会收到明确报错，规则成为强制不变式（而非"没人调用"的约定）。

**验证**：编译通过；`UserServiceImplTest` 新增 `testUpdateUserStatus_AdminCannotBeDisabled` 用例（断言抛 `BusinessException`、不调 `updateById`、不触发 Redis 交互）

**概念**：Enforcement gap（不变式碎片化）。"被封禁的用户不能持有任何有效凭证"是全局规则，但四个发证口（user login / user refresh / admin login / admin refresh）里只有一个登记在册、没有一个查禁用状态。修复模式：在每个发证口补齐同一套动作（登记 + 校验 + 轮换），或收敛到 service 唯一一处。详见附录 B。

**H2 补丁 — 扫荡循环加固** ✅ 已完成（commit `a0f0edd`）：

**问题**：`updateUserStatus` 的扫荡循环对 `user:tokens:{id}` 集合里每个 token 调 `jwtUtil.getExpirationFromToken(token)`，过期 token 会抛 `ExpiredJwtException` → 整个禁用请求失败（"系统繁忙"）。由于 `userMapper.updateById(user)` 在扫荡之前已自动提交，数据库实际已禁用，但前端报错、活 token 未拉黑、集合未清理（重试还炸）。

**根因**：`user:tokens:{id}` 集合无 TTL，用户异常退出（不调 logout）的死 token 永久残留。低危清单当时判断"无害但集合无限增长"，低估了——扫荡会因死 token 崩溃。

**改动**：`updateUserStatus` 扫荡循环体加 `try-catch (JwtException)`，死 token 跳过拉黑继续扫，集合整体 `delete` 一并清理。新增测试 `testUpdateUserStatus_DisableSweepSkipsExpiredTokens` 验证混合 token 场景。

#### H6 spec_hash 漂移 ✅ 已完成

**目标**：`SkuServiceImpl`

**改动**：
- 新增 `normalizeSpecKey(specs)`：每个 spec 归一化为 `templateId:itemId` 条目（`templateId==null` 记 `"default"`），条目排序后 `|` 连接成多重集 key，与 name/value、顺序无关；null/empty specs → `""`
- 规格去重不再依赖存储的 hash 字符串相等：`previewSkusByTemplate` 改用存量 SKU 的 specs 现算归一化 key 建映射（`getSkusBySpu(spuId, null)` 含停用行，避免停用 SKU 的组合被误判为新建），兼容 seed 的 `auto_c*_i*` 与 MD5 两种存量 hash，零数据迁移
- `computeSpecHash` 重写为 `md5(normalizeSpecKey(specs))`：新数据统一 32 位 hex（VARCHAR(64) 安全），归一化 key 相同 ⟺ 存储值相同 → DB 唯一键 `uk_spu_specs` 对新数据真正生效；顺带消除 null templateId 排序 NPE 与同 templateId 排序不稳定（旧实现仅按 templateId 排序，多重集结果随输入顺序漂移）
- `createSku` 保存前按归一化 key 与同 SPU 存量比对，冲突抛 `BusinessException("该规格组合的SKU已存在")`；`updateSku` 改规格时排除自身做同款比对（补齐文档范围外的 update 路径，否则改规格仍可制造重复组合）
- `SkuServiceLogicTest` 新增 name/value 无关、null templateId、多重集乱序、key 区分度、MD5 hex 格式 5 个用例；`SkuServiceImplTest` 新增 createSku 撞 seed 格式存量行抛异常、正常插入、updateSku 冲突抛异常 3 个用例

**验证**：`mvn compile` 通过；`mvn test -Dtest='SkuServiceLogicTest,SkuServiceImplTest'` 全绿（LogicTest 10/10、ImplTest 20/20）

**决策**：
- 路线选"改代码兼容 seed"而非"脚本把 auto_* 重写成 MD5"：零迁移、对任意存量 hash 格式免疫，避免"seed 后必跑迁移"的永久运维耦合（决策记录见第六节）
- 新数据存 MD5(归一化 key)：碰撞概率 ~10⁻³⁸ 工程上可忽略，且应用层比对不依赖 MD5；MD5 仅作 DB 唯一键的第二道防线，专门封死"应用层检查到 INSERT 之间"的并发 TOCTOU 窗口
- createSku/updateSku 冲突报错而非跳过：与 H2 的 BusinessException 用法一致，前端直显文案

**H6 补丁 — 软删行复活** ✅ 已完成：

**问题**：上线后管理端保存 SKU 报 `DuplicateKeyException: Duplicate entry '323-6b337cc...' for key 'uk_spu_specs'`。根因：`uk_spu_specs (spu_id, spec_hash)` 是不含 `delete_time` 的硬唯一键，而软删除行（`delete_time>0`）仍占据槽位；应用层 `checkSpecComboUnique` 只查存活行（正确），放行后 INSERT 撞墓碑。触发链路纯 UI 可达：**删除 SKU（软删）→ 再点生成（墓碑组合显示为"新行"）→ 保存** → createSku 撞墓碑。该缺陷旧代码同样存在（删除旧格式 MD5 行后重建必炸），只是 seed 的 `auto_*` 格式掩盖了它；H6 统一新数据格式后暴露。

**改动**（用户方案：复活墓碑，保 sku_id 不断订单引用）：
- `checkSpecComboUnique` → `findSpecComboRow`：一条查询查该 SPU 全部行（含墓碑），归一化 key 匹配；存活命中立即返回，仅墓碑命中返回 delete_time 最大的
- `createSku`：命中存活行抛 `BusinessException`（不变）；命中墓碑行 → `resurrectSku`：保留 `id`/`createTime`，重写 specs/specHash、`deleteTime=0L`（不能是 NULL——存活判断全是 `eq(deleteTime,0)`，NULL 会令行从所有查询消失）、`status=1`；price/stock/image 入参非空才覆盖；清缓存 + syncStockToCache。附带收益：并发 create 撞同一墓碑都走 updateById 同一行，天然幂等
- `updateSku`：仅墓碑命中时 `freeDeletedSlot` 把墓碑 hash 改写为 `原值#del{deleteTime}` 释放槽位（带重复释放守卫，防 hash 超 VARCHAR(64)），再继续本行更新——封死"改规格撞墓碑"（管理端 specs 只读但保存真实写库，此路径 UI 暂不可达，仍防御性封死）
- 存量墓碑零处理：挡路的墓碑在下次创建同组合时被直接复活，其余自愈
- `SkuServiceImplTest` 新增 5 个用例：撞墓碑复活（不 insert、原 id、deleteTime=0）、多墓碑取最近删除、存活优先于墓碑、update 释放墓碑槽位、已释放墓碑跳过重复改写

**验证**：`mvn compile` 0 错误；`SkuServiceLogicTest` 10/10、`SkuServiceImplTest` 25/25 全绿

**环境插曲**：构建一度全量报 Lombok 符号缺失（Result/OrderServiceImpl 等 `@Data`/`@Slf4j` getter 全丢）——机器 JAVA_HOME 被切到 JDK 25.0.4.1，Lombok 1.18.30 不支持 JDK 22+，注解处理静默失效，与代码无关。用 `set JAVA_HOME=C:\Java\jdk-21` 覆盖后恢复（WSL 侧 `mvn` 是 `cmd.exe /c mvn` 包装脚本，需 cmd 内 set 前缀传环境变量）。待决：JAVA_HOME 切回 jdk-21 或升级 Lombok。

## 七、概念附录

### A. CAS（Compare-And-Swap）与 TOCTOU

**问题**：`check-then-act` 模式（先查状态再改状态）在并发下会被人插队。`@Transactional` 只保证单条语句原子，不保证"检查过的条件一直成立"。

**修复**：把检查焊进 SQL 的 WHERE（CAS），失败抛异常掀桌子回滚。

**项目里的例子**：
- ✅ `confirmReceive`（3→4）、`refundOrder`（2/3→6）、`processPaymentSuccess`（1→2）都用了 CAS
- ❌ `cancelOrder`（1→5）漏了 → H1 修复

**类比**：抢票时你看了眼座位表（A 区 3 排还有座），去付款的路上别人坐下了，你回来直接把名字写上去，还把人家涂了。`updateById` 就像 `git push --force` 旧本地副本；CAS 是 `git push` 带 rebase 检查。

### B. Enforcement gap（不变式碎片化）

**问题**：全局规则（如"被封禁的用户不能持有任何有效凭证"）横跨多套状态（DB `user.status` / JWT+Redis 凭证集），但只在部分口子强制执行。每个方法局部看都"职责单一、逻辑正确"，拼起来不变式就漏风。

**修复**：在每个发证口补齐同一套动作（登记 + 校验 + 轮换），或收敛到 service 唯一一处。

**项目里的例子**：
- ✅ `UserController.login:37` 有 `sAdd` 登记
- ❌ `refreshToken`、`AdminAuthController.login`、`AdminAuthController.refresh` 不登记 → H2 修复

**类比**：开除员工 = 收走门禁卡（拉黑登记集），但这家公司：门禁只认"报废卡清单"、不认花名册（拦截器不查 status）；员工可以自助复制卡且复制卡不用报备（refresh 不登记）；补办柜台不查离职名单（login 不查 status）。收卡收得再勤快也没用。

### F. 优雅降级 —— 非关键字段的校验不得阻断主流程

**问题**：把"输入非法"和"请求该拒绝"当成同一种严重度。头像 URL 是装饰性字段，却因为抛异常成了整个登录/保存流程的硬前置 —— 一个脏值（空串、旧缓存的 wxfile://）就能打死全部用户。

**修复模式（按字段分级）**：
- 钱/权限相关字段：严格校验，异常掀桌子（抛异常回滚）
- 装饰性/体验性字段：校验但优雅降级 —— 非法时不写入、warn 留痕可观测

**本项目教训**：
- ❌ 第一版：非法 avatarUrl 抛"头像地址不合法" → 上传失败发空串 → 全站无法登录
- ✅ 修正版：`StringUtils.hasText` 跳过空串 + 非法值 `log.warn` 后忽略；前端双保险（空值不发、非 http 不发）

**类比**：门禁系统因为工牌系统里的头像照片上传失败，就拒绝你本人进楼。工牌可以没有照片，人必须能进门。

**相关概念**：客户端本地路径（`wxfile://`、`blob:`、`file://`）不是 URL —— 它们只在产生它们的客户端进程内有意义，且多为临时资源。任何"存库前 URL 校验"都应以 `http(s)` scheme 为最低门槛。

### C. 掀桌子 vs 补偿（两种失败处理流派）

**分界线**：失败后能不能"当作没发生"？

| 流派 | 适用场景 | 项目里的例子 |
|---|---|---|
| **掀桌子**（rollback） | 无外部不可逆动作，失败即全回滚 | `cancelOrder`、`confirmReceive`、`refundOrder` 里 `payService==null` 时抛异常回滚 CAS |
| **补偿**（compensation） | 外部不可逆动作已发生（钱已扣/货已发/短信已发） | `processPaymentSuccess` 的 ④ 自动退款（钱已扣，订单已取消，补偿退款） |

**关键**：事务能回滚数据库，回滚不了世界。`refundService.create()`（`PayServiceImpl:419`）是 HTTPS 请求，微信已受理即不可逆。所以 `refundOrder` 用 claim-first（先 CAS 占位 6，事务外调微信），失败时保持 6 等回调自愈。

### D. 事务内操作顺序的防御性布局

**原则**：把裁决（CAS + 失败抛异常）放在事务的最后一步。裁决通过 = 终局，此后没有任何可能失败的写操作；裁决失败 = 掀桌子，此前做的一切全部作废。

**对比**：
- ✅ `cancelOrder`（H1 修复后）：还库存 → CAS 状态 → 失败抛异常回滚。裁决在最后，失败方向干净（什么都没发生）
- ❌ 假设反过来：CAS 状态 → 还库存。裁决通过后还留着一个可失败的步骤，若还库存失败被 catch 吞掉 → 提交 → "已取消但库存没还"永久落库

**例外**：`processPaymentSuccess` 的"裁决不在最后"是对的，因为它是补偿流派——钱已扣（外部不可逆），必须记录事实（payment_record=PAID）然后补偿（退款）。这里的"半完成状态"是故意的且可见的，立即有补偿在同一个事务里，补偿失败也有钉钉告警兜底。

### E. 盲写的三种形态

1. **脑补契约**：前端想象了一个后端没有的接口（H3 头像上传 404）。判断技巧：凡是"前端用了后端不存在的路径"，基本可以断定那一段前端是从需求脑补的，而不是对着 controller 写的。
2. **局部自洽但全局漏**：每个方法职责都自洽，缺的是跨方法的约定（H2 封禁失效、H1 取消竞态）。
3. **不变式碎片化**：全局规则只在部分口子强制执行（H2 的四个发证口只有一个登记）。
