# 商城单体项目（锁具+胶类+当地专线物流园）项目规划文档

---

**文档版本**：V1.0
**撰写日期**：2026年3月28日
**项目定位**：自用工具型商城（解决家人店面实际运营需求）+ 全栈开发学习项目
**目标读者**：本人及家人（实际使用者）、未来面试官（项目展示）

---

## 一、项目背景与目标

### 1.1 项目起源

我家在[所在城市]经营一家五金店，主要销售锁具和胶类商品（包括AB胶、玻璃胶、密封胶等工业/民用胶类产品）。店铺经营多年，客户群体相对稳定，主要包括附近居民、装修师傅、小型工程队等。

目前处理订单的方式比较传统：客户通过微信或电话下单，描述商品名称和数量，我们手动记录后再安排发货。这种方式存在几个明显的问题。

第一个问题是沟通成本高。客户需要打字或发语音描述商品，有时候商品名称不准确（比如把“玻璃胶”说成“透明胶”），需要反复确认才能准确理解需求。

第二个问题是订单容易遗漏或混淆。微信消息太多时，可能漏看客户的订单信息；不同客户的订单混在一起，难以快速统计当日有哪些订单需要处理。

第三个问题是库存管理不清晰。不知道某个商品还剩多少库存，有时候客户下单后才发现没货，只能临时调货影响客户体验。

第四个问题是无法数据化运营。没有销售数据统计，不知道哪些商品卖得好、哪些是滞销品，无法基于数据做进货决策。

基于以上痛点，我希望开发一个小程序加Web管理端的商城系统，让客户能够自主下单，让店铺能够系统化管理订单和库存。这个项目既能解决家里的实际问题，也能作为我的全栈开发实战项目，积累真实的项目经验。

### 1.2 项目定位

本项目是一个**自用工具型轻量商城**，定位明确不同于商业化电商平台。核心目标是替代微信聊天接单和手写记账，实现订单处理的数字化。考虑到店铺的实际规模和客户群体，不追求复杂的功能和庞大的用户量，而是聚焦于稳定、实用、易用。

作为开发学习项目，本项目需要覆盖完整的技术栈，包括前端小程序开发、后端接口开发、数据库设计、支付集成、部署运维等环节。通过这个项目，我期望掌握企业级应用开发的核心技能，为未来的职业发展打下基础。

### 1.3 目标用户

本系统有两类核心用户群体。

第一类是**C端消费者**，即来店客户的亲友或有采购需求的个人消费者。他们通过小程序浏览商品、下单支付、查看物流。他们的特点是：对微信生态熟悉、可能不太会使用复杂的电商平台、需要简单直接的操作流程、年龄和IT能力分布广泛。

第二类是**B端运营人员**，即家人或店员。他们通过Web管理端处理订单、管理商品、查看数据。他们的特点是：IT能力有限、更习惯图形界面操作而非命令行、需要一眼看清当日待办事项、操作频率高于普通用户。

### 1.4 成功标准

项目的成功标准分为实用价值和成长价值两个维度。

在实用价值方面，客户能够通过小程序完成下单流程，无需额外沟通确认；店铺每天早上打开管理端，能够一目了然看到待发货订单列表；订单信息完整准确，减少因沟通歧义导致的错单漏单；商品库存实时可查，下单前能确认是否有货。

在成长价值方面，完成项目后能够独立搭建Spring Boot后端项目并完成接口开发；掌握uni-app开发小程序的能力，能够完成页面布局、数据绑定、接口调用；理解前后端分离架构的设计思想；掌握Git版本控制的基本使用方法；能够将项目部署到云服务器并正常运行；积累一个可用于面试的全栈项目经验。

## 二、功能需求说明

### 2.1 功能设计原则

在设计功能时，我遵循以下原则。

第一个原则是**聚焦核心流程**。先解决最重要的问题：小程序能让客户下单，管理端能让店铺看到订单。其他功能如数据统计、复杂的物流管理等，都是锦上添花，可在核心流程稳定后再迭代。

第二个原则是**操作尽量简单**。考虑到B端用户的IT能力，界面要直观、操作要简洁，尽量减少输入框和下拉选择，一个页面解决一个问题。

第三个原则是**物流功能简化**。物流选项在管理端预先配置好固定的5-10个选项（如德邦、顺心捷达、安能物流等），用户下单时只能选择已有选项，不支持用户自定义输入。这个简化方案足以满足实际需求，同时大幅降低开发复杂度。

### 2.2 C端小程序功能

小程序面向消费者，核心是提供便捷的下单体验。

**商品浏览**模块支持按分类查看商品（锁具、胶类两个一级分类，每个分类下有具体的商品列表）；支持关键词搜索（输入商品名称或规格快速找到商品）；商品详情页展示商品图片、名称、规格、价格、库存状态。

**购物车**模块支持将商品加入购物车并设置数量；支持修改商品数量或删除商品；支持勾选商品后一键结算。

**下单支付**模块支持选择收货地址（支持新增、编辑、删除收货地址，默认为上次使用的地址）；支持选择配送方式（从管理端配置的物流列表中选择）；支持使用微信支付完成付款；支付成功后生成订单并跳转至订单列表。

**订单管理**模块支持查看全部订单（待付款、待发货、已发货、已完成、已取消、已退款）；支持查看订单详情包括商品列表、物流信息；支持对未付款订单发起退款（取消订单）。

**个人中心**模块支持展示用户基本信息；支持管理收货地址；支持查看订单记录。

### 2.3 B端管理端功能

管理端面向店铺运营人员，核心是提供高效的订单处理能力。

**仪表盘首页**展示今日订单数量、今日销售额、今日待发货数量；展示最近的订单列表（按时间倒序，默认显示20条）；提供快捷入口如待发货订单处理。

**订单管理**模块支持查看所有订单列表，支持按订单状态、日期范围筛选；支持查看订单详情包括客户信息、商品明细、支付信息、物流信息；支持对已付款订单标记发货并填写物流信息；支持处理退款申请。

**商品管理**模块支持新增、编辑、删除商品；支持设置商品上下架状态；支持管理商品分类；支持设置商品规格（如锁具的尺寸、胶类的容量）；支持设置商品库存数量。

**用户管理**模块支持查看注册用户列表；支持按省市筛选用户；支持查看用户的基本信息和订单记录。

**物流管理**模块支持新增、编辑、删除物流选项；支持多个联系电话管理；支持按城市筛选物流；支持启用或禁用物流选项（禁用的选项不显示给用户）；这是唯一一个需要手动维护的配置功能。

**数据统计**模块支持查看订单统计数据（按日、周、月维度）；支持查看商品销售排行；支持查看订单状态分布。

### 2.4 功能优先级

我将功能分为三个优先级批次。

**P0必须实现**（MVP，核心流程必须走通）：商品浏览与搜索、小程序下单支付、管理端查看订单、微信支付集成、基础物流选择（固定选项）。

**P1应该实现**（完善体验）：购物车功能、收货地址管理、订单状态流转、订单发货与物流信息更新、商品上下架管理、库存管理。

**P2可以迭代**（锦上添花）：订单筛选与高级搜索、数据统计报表、用户管理、登录注册验证码验证。

### 2.5 边界与限制

明确以下边界和限制，避免开发过程中无限扩张。

小程序仅支持微信小程序平台，暂不开发支付宝小程序或H5版本。管理端仅支持桌面端浏览器访问，暂不开发移动端管理App。支付仅集成微信支付，暂不支持其他支付方式。物流仅支持从固定列表中选择，暂不支持用户自定义输入物流信息。订单处理以人工操作为主，暂不实现自动化流程。

## 三、技术方案

### 3.1 技术架构

本项目采用经典的前后端分离架构，前端负责用户界面展示，后端负责业务逻辑和数据处理。这种架构的优势在于职责分离清晰、前后端可独立开发、前端可复用、便于分工协作。

系统的整体架构如下：微信小程序（C端用户）通过HTTPS与后端API通信；Web管理端（B端运营人员）同样通过HTTPS与后端API通信；后端服务使用Spring Boot框架开发，运行在云服务器上；数据库使用MySQL存储所有业务数据；文件存储使用云存储服务（如阿里云OSS或七牛云）存储商品图片。

```
┌─────────────────────────────────────────────────────────────┐
│                        客户端层                              │
├─────────────────────────┬───────────────────────────────────┤
│    微信小程序           │         Web管理端                 │
│    (uni-app)            │         (Vue3 + Element Plus)      │
└───────────┬─────────────┴───────────────┬───────────────────┘
            │                             │
            └──────────┬──────────────────┘
                       │ HTTP/HTTPS
            ┌──────────▼──────────────────┐
            │         API网关层            │
            │    (Spring Boot + MyBatis)  │
            └──────────┬──────────────────┘
                       │
            ┌──────────▼──────────────────┐
            │         数据层                │
            │    (MySQL + Redis缓存)        │
            └─────────────────────────────┘
```

### 3.2 技术选型

**后端技术栈**选择Spring Boot作为主框架，原因如下：Spring Boot是Java企业级开发的事实标准，社区活跃，中文资料丰富；自动配置机制大幅减少样板代码，开发效率高；生态完善，Spring Security、Spring Data等组件开箱即用；我之前学习过Java基础，上手Spring Boot的曲线相对平滑。

选择MyBatis-Plus作为ORM框架，原因如下：对SQL掌控度高，不像JPA那样容易被隐藏实现细节；内置分页、乐观锁等功能，开发便捷；代码生成器可以快速生成基础的CRUD代码；官方文档完善，学习成本低。

选择MySQL作为数据库，原因如下：开源免费，社区成熟；关系型数据库适合本项目的业务场景；单机性能足够支撑初期的数据量；Navicat等可视化工具对新手友好。

**前端技术栈**选择uni-app作为小程序开发框架，原因如下：基于Vue.js语法，学习成本低；一次开发可编译到多个平台（微信、支付宝、H5等）；HBuilderX IDE对新手友好；插件市场有丰富的组件可用。

选择Vue3作为Web管理端框架，原因如下：Vue3是当前最主流的前端框架之一，市场需求大；Composition API让代码组织更清晰；学习Vue3对理解前端工程化很有帮助。

选择Element Plus作为Web管理端UI组件库，原因如下：组件丰富，覆盖了后台系统的常见场景；文档完善，中文友好；样式美观，开箱即用。

**辅助工具**选择Git进行版本控制，原因如下：版本控制是开发必备技能；GitHub/Gitee可托管代码，展示项目能力；熟练使用Git对团队协作很有帮助。

选择Docker进行部署，原因如下：环境一致性好，开发和生产环境统一；部署简单，一条命令即可启动服务；云服务器厂商普遍支持Docker。

### 3.3 数据库设计

本项目的核心数据表设计如下。

**用户表（user）**存储用户基本信息，包括用户ID（主键自增）、微信OpenID（用于微信授权登录）、昵称、头像URL、手机号、创建时间、更新时间。

**收货地址表（address）**存储用户的收货地址信息，包括地址ID（主键自增）、用户ID（外键关联用户表）、收货人姓名、手机号、省市区地址、详细地址、是否默认地址、创建时间、更新时间。

**商品分类表（category）**存储商品分类信息，包括分类ID（主键自增）、分类名称（如锁具、胶类）、排序权重、是否启用、创建时间。

**商品表（product）**存储商品信息，包括商品ID（主键自增）、分类ID（外键关联分类表）、商品名称、规格描述、图片URL、价格（单位分，避免浮点数精度问题）、库存数量、是否上架、创建时间、更新时间。

**订单表（order）**存储订单主信息，包括订单ID（主键自增）、订单编号（业务唯一标识）、用户ID（外键关联用户表）、收货地址ID（外键关联地址表）、订单状态（待付款/待发货/已发货/已完成/已取消/退款中/已退款）、订单总金额、物流方式ID（外键关联物流表）、物流单号、支付时间、发货时间、收货时间、创建时间、更新时间。

**订单明细表（order_item）**存储订单中的商品明细，包括明细ID（主键自增）、订单ID（外键关联订单表）、商品ID（外键关联商品表）、商品名称（下单时的快照，避免商品信息变更影响历史订单）、商品规格（下单时的快照）、商品单价（下单时的快照）、购买数量、小计金额。

**物流方式表（logistics）**存储可选的物流方式，包括物流ID（主键自增）、物流名称（如德邦物流）、物流编码、排序权重、是否启用、创建时间、更新时间。

### 3.4 核心接口设计

**用户模块**接口包括微信登录（通过wx.login获取code，后端换取openid并返回token）、获取用户信息（需要登录态）、更新用户信息。

**商品模块**接口包括获取分类列表、获取某个分类下的商品列表、搜索商品、获取商品详情。

**购物车模块**接口包括获取购物车列表（需要登录态）、添加商品到购物车、修改购物车商品数量、删除购物车商品。

**订单模块**接口包括创建订单（需要登录态，传入商品列表、地址ID、物流ID）、获取订单列表（需要登录态，支持状态筛选）、获取订单详情（需要登录态）、申请退款（需要登录态）、确认收货（需要登录态）。

**订单管理模块**接口（需要管理员权限）包括获取所有订单列表（支持多条件筛选）、获取订单详情、修改订单状态、填写物流信息。

**商品管理模块**接口（需要管理员权限）包括创建商品、编辑商品、删除商品、修改商品上下架状态、修改库存数量。

**物流管理模块**接口（需要管理员权限）包括获取物流列表、添加物流方式、编辑物流方式、删除物流方式、启用禁用物流方式。

### 3.5 微信支付集成

微信支付是本项目的技术难点之一，需要认真对待。

**支付流程**如下：用户在微信小程序内选择商品下单；前端调用后端创建订单接口，获取订单号和支付参数；前端调用wx.requestPayment调起微信支付；用户完成支付后，微信服务器回调后端接口通知支付结果；后端更新订单状态为已支付。

**注意事项**包括：支付密钥（APIv3密钥、证书）必须妥善保管，不能泄露也不能提交到代码仓库；支付回调必须正确处理，包括签名验证、幂等性处理（防止重复通知）；测试阶段使用微信支付的沙箱环境，避免使用真实资金。

### 3.6 非功能性需求

**性能需求**包括页面加载时间不超过3秒（用户体验的基本保障）、接口响应时间不超过1秒（99%的情况下）、能够支撑同时10个用户在线的基本并发。

**安全需求**包括用户密码或敏感信息加密存储；接口调用需要身份验证（Token机制）；管理端接口需要额外验证管理员权限；防止SQL注入、XSS攻击等常见安全问题。

**可用性需求**包括系统可用性目标为95%（每天有几个小时的维护窗口是可以接受的）；数据库每日自动备份；关键操作记录日志。

**兼容性需求**包括小程序兼容微信版本8.0以上；管理端兼容Chrome、Edge、Safari最新版。

## 四、开发计划

### 4.1 项目阶段划分

我将整个项目分为五个阶段，每个阶段有明确的目标、交付物和时间预期。

**第一阶段是环境准备与项目搭建（第1周）**。主要目标是完成开发环境的配置，创建可运行的项目框架。主要工作包括购买云服务器并安装基础环境（CentOS + Docker + Nginx）；配置域名和SSL证书；初始化Spring Boot项目，配置MySQL数据源；初始化uni-app项目，配置微信开发者工具；初始化Vue3项目，配置Element Plus；创建Git仓库，建立项目结构；部署后端服务到服务器，确保可以访问。这个阶段的交付物是一个可访问的空白项目框架，包含后端API服务、小程序项目、管理端项目。

**第二阶段是后端核心功能开发（第2-3周）**。主要目标是完成所有后端接口的开发。主要工作包括用户模块（微信登录、Token验证）；商品模块（分类查询、商品列表、商品详情）；物流管理模块（物流CRUD）；地址管理模块（地址CRUD）；订单模块（创建订单、订单列表、订单详情、退款）；商品管理模块（商品CRUD、上下架、库存）；微信支付模块（统一下单、支付回调）。这个阶段的交付物是完整的后端API，测试通过后可正常调用。

**第三阶段是小程序端开发（第4-5周）**。主要目标是完成小程序的所有页面和交互。主要工作包括页面框架搭建（底部TabBar、页面路由）；商品浏览页面（分类页、列表页、详情页）；购物车页面（添加、修改、删除、结算）；下单支付流程（地址选择、物流选择、微信支付）；订单列表和详情页面；个人中心页面（地址管理、订单入口）。这个阶段的交付物是一个完整的小程序，可进行完整的下单流程测试。

**第四阶段是管理端开发（第6-7周）**。主要目标是完成管理端的所有功能。主要工作包括登录与权限验证；仪表盘首页（数据概览、快捷入口）；订单管理页面（列表、筛选、处理发货）；商品管理页面（CRUD、库存调整）；物流管理页面（配置物流选项）；用户管理页面（查看用户列表）。这个阶段的交付物是一个完整的管理端，可完成日常运营操作。

**第五阶段是联调测试与部署（第8周）**。主要目标是确保所有功能正常运行并部署上线。主要工作包括前后端联调，修复接口对接问题；完整业务流程测试（注册到下单到发货）；Bug修复与优化；上线部署与监控配置；项目文档编写（README、接口文档）；Git代码整理与提交记录规范。这个阶段的交付物是可正式访问的线上系统，包含完整的文档。

## 六、风险与应对

### 6.1 技术风险

**风险1：微信支付对接复杂，容易踩坑**。微信支付的文档虽然详细，但涉及的步骤和配置项较多，对于新手来说容易出错。应对措施是提前阅读微信支付官方文档，理解支付流程的每个环节；先在沙箱环境测试，确认流程正确后再切换到正式环境；使用微信官方提供的SDK，减少自己造轮子的风险；遇到问题优先查看微信支付社区和常见问题文档。

**风险2：技术栈不熟悉导致进度慢**。虽然选择了相对容易上手的技术栈，但对于一个完整项目来说，涉及的知识点仍然很多。应对措施是每个模块开始前先看官方教程和基础示例，不要盲目动手；遇到问题时先理解问题的本质，再搜索解决方案；善用AI工具辅助学习，但不要完全依赖，保持独立思考；预留足够的调试时间，不要把计划排得太紧。

**风险3：前后端联调时问题多**。接口定义不一致、数据格式不匹配、跨域问题等是常见痛点。应对措施是后端接口设计时充分考虑前端需求，文档先行；使用接口管理工具（如Apifox）维护接口文档，便于前后端对照；前后端开发过程中保持沟通，及时对齐字段定义和返回格式。

### 6.2 项目风险

**风险4：家人需求变更或增加**。实际使用中，家人可能会提出新的需求或修改原有需求。应对措施是在开发前充分沟通，把核心功能和边界确认清楚并形成文档；开发周期内不接受大的需求变更，所有变更记录到下一期计划；采用迭代开发模式，核心流程优先完成，保证项目能交付使用。

**风险5：时间不够用**。工作和生活可能占用大部分时间，导致项目进度拖延。应对措施是在开始前评估自己的时间投入能力，制定合理计划；预留buffer时间应对意外情况；必要时可以简化功能范围，保证核心流程可用；坚持每日或每周推进，避免长时间中断导致遗忘上下文。

### 6.3 运营风险

**风险6：系统上线后家人不会用**。管理端的操作对于IT能力有限的家人来说可能存在门槛。应对措施是界面设计尽量直观，减少专业术语的使用；编写清晰的操作手册，截图配合文字说明；初期自己代为操作，让家人先熟悉流程；收集使用反馈，针对性地优化体验。

**风险7：订单出现异常无法处理**。如支付成功但订单未创建、物流信息填写错误等情况。应对措施是设计完善的订单状态机制和日志记录；提供管理端手动修复订单状态的功能；制定异常订单的处理流程和责任人。
